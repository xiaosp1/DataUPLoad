## 二、项目背景

集团下属工厂存在四类共性问题：一是海康视觉、包装机 PLC、点数机 PLC 等设备数据各自为政，无法统一汇聚，也无法上传 MES；二是生产过程以人工巡检和经验判断为主，车间主任和工艺工程师对实时状态、产量、良率、故障缺乏即时感知；三是设备故障被动响应，停机后才知道，缺少诊断与预警；四是海康缺陷数据与工艺参数没有自动关联，根因分析靠人工事后比对。

为此，集团决定建设工业数据采集与智能分析平台，打通"设备采集→本地存储→MES上传→分析展示→AI诊断"全链路。青州试点后复制至23个车间。

## 三、项目目标

**总体目标**：采得全、传得稳、看得清、算得准、配得灵、可审计。

- **采得全**：对接海康视觉、包装机PLC（OPC-UA）、点数机PLC（EIP）三类数据源，覆盖状态、工艺参数、产量、故障、缺陷等数据。
- **传得稳**：稳定上传MES，支持断网缓存、自动补传、本地去重，数据丢失≤5分钟。
- **看得清**：提供工厂总览、车间看板、设备详情、工位端四类视图，大屏刷新≤30秒。
- **算得准**：提供OEE、SPC、帕累托、趋势、相关性等传统分析，结合本地AI提供故障诊断（MVP）、预测维护、工艺优化、根因分析、自动报告。
- **配得灵**：采集点位、报警阈值、上传规则、班次、字典全部可视化配置，支撑快速复制。
- **可审计**：写PLC、改配置、导出数据、启停采集等关键操作全程留痕。

**关键指标**：

| 指标 | 目标 |
|---|---|
| 数据链路可用性 | ≥99%（含补传） |
| 数据丢失窗口 | ≤5 分钟 |
| 大屏刷新延迟 | ≤30 秒 |
| 单车间日处理能力 | ≥500 万条 |
| 数据在线留存 | ≥1 年 |
| MES 上传成功率（含补传） | ≥99.5% |
| 5 天 MVP | 海康采集 → 本地存储 → MES 上传通道跑通 |
| 单车间复制部署（三期） | ≤1 人日 |

## 五、功能范围

### 5.1 数据采集

#### F-COL-01 海康视觉采集

| 维度 | 说明 |
|---|---|
| 输入 | 海康视觉中控 HTTP 接口 |
| 处理 | 定时轮询+新报警事件触发，抓取缺陷、报警等结构化字段写入本地；一期不抓图片 |
| 输出 | 缺陷、报警结构化记录，供看板、报表、AI和MES上传使用 |
| 业务规则 | 轮询周期可配，报警类即时触发；海康不可达时告警并断点续采；日均约100万条；记录带采集时间戳。 |

#### F-COL-02 包装机 PLC 采集（OPC-UA）

| 维度 | 说明 |
|---|---|
| 输入 | 车间包装机 PLC（欧姆龙 NX102-9000、汇川 AC801 等），OPC-UA 协议 |
| 处理 | 按配置点位读取温度、压力、速度、计数、状态、故障代码、配方号、产量等（约50点/台），支持轮询（默认1分钟）+变化主动上报 |
| 输出 | 包装机参数、状态、产量、故障时序记录 |
| 业务规则 | 每车间8~16台；频率与变化上报点位可配；点位必须可视化配置（地址、类型、频率、阈值等），不写死；断线自动重连并标记"通讯异常"；支持反向写入（F-COL-05）。 |

#### F-COL-03 点数机 PLC 采集（EtherNet/IP）

| 维度 | 说明 |
|---|---|
| 输入 | 手套点数机 PLC（欧姆龙），EIP 协议 |
| 处理 | 一期必采设备状态、故障码、节拍；其余点位通过配置随时扩展；同样支持轮询 + 变化触发 |
| 输出 | 点数机状态、节拍、故障时序记录 |
| 业务规则 | ①1 台包装机对应 2~4 台点数机，每车间约 16~64 台；②与包装机通过产线/设备编号关联，支撑节拍与良率分析 |

#### F-COL-04 边缘缓存与断网续传

| 维度 | 说明 |
|---|---|
| 输入 | 所有采集原始数据、MES 待上传数据 |
| 处理 | 数据先落地本地缓存；与中心或 MES 网络不通时持续缓存，恢复后按序补传 |
| 输出 | 本地持久化记录、补传任务状态、缓存水位告警 |
| 业务规则 | ①数据丢失≤5 分钟；②本地生成唯一 ID + 已发送标记防重，保证至少一次交付；③缓存超阈值触发预警，支持人工导出补录；④断网期间采集默认不中断（开关可控） |

#### F-COL-05 写 PLC（工单/配方下发）

| 维度 | 说明 |
|---|---|
| 输入 | ①MES 下发的工单/配方；②本地界面手工录入的工单/配方 |
| 处理 | 写入对应 PLC，PLC/HMI 端人工二次确认后生效 |
| 输出 | 写入结果、操作记录、失败报警 |
| 业务规则 | ①MES 下发与本地录入两种入口都支持；②写失败仅报警不自动重试，避免误写；③所有写操作必须记入审计日志（操作人、时间、设备、内容、结果）；④一期软件端不做权限校验，依赖 PLC/HMI 二次确认 + 审计兜底 |

### 5.2 MES 上传

#### F-UPL-01 数据上传通道

| 维度 | 说明 |
|---|---|
| 输入 | 本地已落地的缺陷/报警/工艺参数/产量/状态/故障/工单结果 |
| 处理 | 按类别封装报文，通过 HTTP 推送 MES；定时批量 + 事件触发并存 |
| 输出 | MES 接收确认、本地上传状态（待传/已传/失败）、上传日志 |
| 业务规则 | ①一期优先打通海康缺陷与报警上传，PLC 数据上传二期补齐；②覆盖产量/计数、故障/报警、缺陷、工艺参数、工单/配方结果、设备状态，原始与聚合都传；③接口规范以 MES 侧现有规范为准（RESTful 或统一网关都适配）；④本地去重防重发 |

#### F-UPL-02 失败重试与补传

| 维度 | 说明 |
|---|---|
| 输入 | MES 失败/超时、网络不可用 |
| 处理 | 失败记录进入待传队列按策略重试；长时间不可达落地缓存，恢复后按时间顺序补传 |
| 输出 | 补传任务、失败告警、成功率统计 |
| 业务规则 | ①缓存超阈值预警并支持人工导出；②上传/补传全留日志便于与 MES 对账；③写 PLC 下行动作失败不重试 |

### 5.4 AI 智能分析

AI 本地部署，数据不出厂；所有 AI 输出均为"辅助建议"，不直接操控设备；不做通用聊天助手。

| 编号 | 功能点 | 输入 | 处理 | 输出 | 业务规则与分期 |
|---|---|---|---|---|---|
| F-AI-01 | **故障诊断（AI MVP）** | 报警事件 + 前后工艺参数/状态 + 历史同类故障与处置记录 | 调用本地模型生成原因分析与处置建议 | 故障原因、推荐处置步骤、相似案例 | **一期首发**；结果标注置信度；用户可反馈有用/无用，用于迭代 |
| F-AI-02 | 智能问答（自然语言查数） | 用户自然语言问题（如"今天 3 号机产量？"） | 解析查询意图，调用数据查询接口 | 数字/图表/简要结论 | 限定在本平台数据范围，不支持闲聊；三期 |
| F-AI-03 | 预测性维护 | 历史状态/故障/参数/维修记录 | 识别潜在故障趋势提前预警 | 设备、风险等级、预计窗口、建议动作 | 标注概率/置信度；与报警中心联动；三期 |
| F-AI-04 | 工艺优化建议 | 工艺参数历史 + 良率/缺陷 + 配方 | 分析参数区间与质量/产量关系 | 推荐参数区间、预期收益、风险提示 | 建议仅供参考，下发需走写 PLC 流程；三期 |
| F-AI-05 | 缺陷根因分析 | 海康缺陷 + 同时窗工艺参数/状态/配方/工单 | 关联缺陷与参数异常，分析可能根因 | 根因排序、关联证据、排查方向 | 是海康与 PLC 数据联动核心价值场景；三期 |
| F-AI-06 | 自动生成报告 | 指定周期/车间/主题统计数据 | 按模板生成文字+图表的报告草稿 | 可编辑/导出的日/周/月报告 | 分车间主任与厂长视角；四期 |

## 六、非功能需求

**性能与容量**：单车间约 48 台 PLC、约 2400 点位，日数据量 400~500 万条；青州 7 车间约 3000 万条/天；全集团 23 车间约 1 亿条/天；数据在线留存≥1 年；常规历史查询（单车间/单设备/单日）≤5 秒，大范围查询允许异步。

**可靠性**：数据丢失≤5 分钟；MES 上传至少一次、本地去重防重；断网/MES 故障/PLC 断线均本地缓存、恢复补传；核心服务异常自动重启；写 PLC 失败不自动重试。

**安全合规**：一期不做细粒度权限与数据加密，但预留扩展位；关键操作必须审计；AI 本地部署、数据不出厂；写 PLC 必须经 PLC/HMI 二次人工确认。

**可运维与可复制**：一期人工部署、开发自运维；远程运维、外部告警通道预留接口；设备与点位必须模板化、可批量复制，支撑多车间快速接入。

**易用性**：大屏与工位端无需培训即可理解；设备详情页层次清晰便于工程师定位问题；配置界面提供模板和批量导入，降低现场配置门槛。

## 七、分期计划

### 7.1 第一里程碑：5 天 MVP 数据链路打通（最高优先级）

**目标**：5 天内打通最小数据闭环，证明平台可行，作为一切后续功能的基础。

**范围**：①从海康 HTTP 接口抓取缺陷与报警结构化数据；②数据落地本地存储可查；③通过 HTTP 推送到 MES（或模拟端点验证通路）；④采集服务自启动、失败缓存重试；⑤最简状态/数据预览界面证明数据在流动。

**交付物**：可运行的采集程序、基础运行日志与简单状态界面、链路验证记录（抓取/写入/上传条数与失败率）。

**本阶段明确不做**：PLC 采集、AI、完整大屏、OEE/SPC、配置界面、权限。

### 7.2 一期（约 2~3 个月）：青州试点核心闭环

- 三类数据源（海康+包装机+点数机）采集全部打通；
- 实时监控四类视图上线（工厂大屏/车间看板/设备详情/工位端）；
- 海康数据稳定上传 MES；
- AI 首发：故障诊断（报警时给出原因+处置建议）；
- 断网缓存、补传、自启动等可靠性基础能力；
- 设备/点位/字典基础配置与审计日志。

### 7.3 二期（约 +2 个月）：分析完善 + PLC 数据上传 MES

- PLC 数据上传 MES（产量/工艺/状态/故障/工单结果）；
- OEE、SPC、日周月报表、故障帕累托/MTTR/MTBF、趋势回放、相关性分析；
- 报警规则引擎（阈值+组合条件）；
- 点位配置界面完整可用，支持模板批量复制；
- 近 3 个月自动备份与完善的 Excel 导出。

### 7.4 三期（约 +2 个月）：AI 进阶 + 多车间复制

- AI 扩展：预测性维护、工艺优化、根因分析、智能问答；
- 沉淀多车间复制工具包（设备/点位模板、批量配置、复制手册）；
- 单车间部署配置≤1 人日；
- 青州内部跨车间对比分析。

### 7.5 四期：多端 + 自动报告 + 全基地推广

- 飞书/微信小程序/Web 端扩展；
- 自动生成并推送日/周/月报告；
- 跨基地汇总 BI（集团管理层视图）；
- 远程运维、飞书/硬件告警通道正式接入；
- 向淮北、江西等基地复制，覆盖全部 23 个车间。

## 八、风险与约束

**主要风险**：

| 风险 | 应对策略 |
|---|---|
| MES 接口规范和测试环境未最终确认 | MVP 阶段先用可替换的上传适配层打通海康链路，正式对接时按 MES 实际规范适配 |
| 多款 PLC、两种协议对接复杂度高 | 青州首批先对接现场在用型号，沉淀设备型号模板；点位全部可视化配置支持现场调整 |
| 车间网络/防火墙/网段隔离 | 边缘工控机本地自治（本地看板+本地缓存+本地采集可独立运行），与 MES/中心仅走有限 HTTP 端口；提前与 IT 确认网络策略 |
| 断网/MES 长时间不可用 | 本地缓存 + 补传 + 水位预警 + 人工导出兜底 |
| 多设备时间不一致影响分析 | 局域网 NTP 对时 + 网关软时间戳 + 漂移告警（技术方案落地） |
| 全集团约 1 亿条/天，存储查询压力大 | 时序存储设计与冷热分层；一期仅承接青州，容量规划先行 |
| 一期 AI 小模型准确率有限 | 输出标注"建议"和置信度，建立人工反馈闭环，从高频可验证场景切入 |
| 单人开发资源紧张 | 严格分期，MVP 只做最小链路，权限/移动端/自动备份/远程运维一律后置 |
| 现场设备/点位/配方/班次频繁变更 | 点位/规则/字典/班次全部配置化，不写死，变更留审计 |
| 写 PLC 误操作风险 | 不自动重试，PLC/HMI 二次确认生效，全量审计，初期只开放必要写入点位 |

**约束条件**：

- **部署**：一期为车间 Windows 工控机（每车间 1 台），局域网；后期扩展机房服务器集中部署。
- **网络**：车间局域网为主，存在防火墙/网闸可能，需支持离线自治与补传。
- **人力**：单人开发，必须严格范围控制、分期交付。
- **时间**：5 天内必须打通海康数据链路 MVP；后续按 2~3 个月一期节奏。
- **数据安全**：AI 本地部署、数据不出厂；一期不做加密和权限，预留扩展位。
- **业务口径**：白班/夜班两班，跨天班次统计一期不做；数据在线留存 1 年；数据丢失容忍 5 分钟。
- **设备**：PLC 以青州现场欧姆龙 NX102-9000、汇川 AC801、欧姆龙 EIP 点数机等型号为准；海康一期只抓结构化文字数据，不抓图片。

## 八、风险与约束

本项目同时跨设备采集、MES 对接、可视化大屏、AI 诊断和车间落地多个环节，且首期以单人开发、青州试点快速验证为主，必须对风险提前识别并给出应对动作。以下风险按“影响程度 × 发生概率”排序，作为项目管理、范围控制和现场联调的依据。

### 8.1 MES 接口规范未定导致对接延期

**风险描述**：当前 MES 侧尚未提供正式接口文档和测试环境，认证方式（JWT、Ticket、统一网关）、报文字段、返回码、批量上限、幂等规则均可能反复调整，极易卡在上传联调阶段，拖慢整体节奏。  
**影响**：无法完成真实上传闭环，项目价值（采数上传 MES）被质疑。  
**应对**：①一期优先采用适配器模式，同时预留标准 RESTful 与英科统一网关两种接入方式，接口调用封装为独立 Uploader，不把 MES 字段散落在业务代码里；②先以本地 Mock 服务跑通采集-上传-补传-幂等全链路，保证链路质量不依赖 MES 环境；③主动向 MES 团队输出我方建议报文模板和字段清单，反向驱动接口冻结；④协议一旦定版，将报文样例和错误码表纳入版本管理。

### 8.2 PLC 点位表不完整、地址经常变动

**风险描述**：现场包装机和点数机品牌型号不完全统一（欧姆龙 NX102-9000、汇川 AC801 等），点位表可能由设备商或电气工程师口头提供，存在地址错、点位缺、改机后未同步的情况，导致采集数据不准甚至读到危险地址。  
**影响**：趋势、OEE、SPC、AI 诊断等所有上层功能都会失真；写 PLC 存在误写风险。  
**应对**：①所有点位必须走可视化配置，不允许写死在代码；②上线前由工艺/设备/IT 三方签字确认点位表，并保存版本；③先接通 1 台包装机+1 台点数机做样本验证，确认地址、类型、单位、缩放比例后再批量复制；④对写 PLC 的地址单独做白名单校验，未配置明确写权限的地址一律拒绝下发；⑤点位变更必须写审计日志，支持快速回滚到上一版本。

### 8.3 现场网络不稳定、防火墙与网段隔离

**风险描述**：车间工控机、PLC、海康视觉、中心服务器、MES 可能分布在不同网段，存在防火墙拦截、偶发丢包、跨 VLAN 不通、与办公网隔离等问题，断网是常态而非异常。  
**影响**：采集中断、上传失败、大屏空白、补传队列积压。  
**应对**：①边缘侧必须具备本地自治能力，断网时继续采集、本地存储、本地展示，网络恢复后自动补传；②关键端口和访问关系在部署前形成网络开通清单，由 IT 提前放通；③对“海康不可达、PLC 断线、MES 不可达、中心不可达”分别定义告警和重试策略；④队列积压超过阈值时本地告警并支持人工导出，避免数据库打满；⑤所有外部调用都设置合理超时和熔断，防止阻塞采集主循环。

### 8.4 工控机硬件性能有限

**风险描述**：车间工控机可能配置参差不齐（CPU 弱、内存小、硬盘老旧），同时运行采集服务、本地 SQLite、WebView 大屏、WPF 壳，高频写入或本地 AI 推理容易造成卡顿、磁盘占满、服务假死。  
**影响**：边缘服务不稳定，现场体验差，直接影响试点口碑。  
**应对**：①边缘端默认关闭本地大模型推理，主要 AI 推理放中心 GPU 服务器，边缘仅保留规则兜底和最小模型（可关）；②写入采用批量+队列，避免逐条写库；③SQLite 只承担边缘缓存和待上传队列，高频历史数据落 TDengine；④上线前检查工控机配置（CPU、内存、磁盘剩余、系统版本），不满足最低配置的先升级或置换；⑤提供一键“诊断模式”，展示 CPU、内存、磁盘、队列深度、采集延迟，方便现场排障。

### 8.5 时间不同步导致数据错乱

**风险描述**：工控机、PLC、海康、MES 各自时钟如果不同步，会导致时序错位、班次统计错误、补传乱序、故障根因分析偏差，严重时 MES 侧按时间戳去重会误判为重复或缺数。  
**影响**：数据可信度下降，报表和 AI 分析都将失真。  
**应对**：①部署 NTP 时间同步，中心服务器作为二级 NTP 源，工控机按固定周期同步；②采集数据同时保留设备时间、边缘系统时间、入库时间三类时间戳，统一以边缘 UTC 时间作为主排序；③启动时检测时钟漂移，漂移超过阈值在大屏和运维页报警；④在培训和上线检查清单中把时间同步作为必查项。

### 8.6 写 PLC 存在误操作与安全风险

**风险描述**：工单/配方写入 PLC 直接影响设备运行，一旦软件误写、参数错误或重复下发，可能导致停机、次品甚至安全事故。  
**影响**：生产事故风险高，属于必须重点控管的环节。  
**应对**：①一期不做自动闭环下发，所有写 PLC 动作必须由人工触发，并经 PLC/HMI 二次确认后生效；②写失败只报警不自动重试，避免重复写入；③所有写操作必须留完整审计记录（操作人、时间、设备、参数、结果）；④写地址做白名单，禁止写未登记地址；⑤对安全相关点位（急停、安全门、限位）一期禁止写入，仅做监控。

### 8.7 AI 诊断结果被误用为唯一决策依据

**风险描述**：AI 故障诊断基于历史案例和实时特征推断，存在误判、漏判和样本不足的可能，如果现场维修人员完全依赖 AI 建议，可能延误维修或误判故障。  
**影响**：降低平台可信度，甚至导致错误操作。  
**应对**：①明确将 AI 定位为“辅助建议”，界面上必须展示置信度和“仅供参考”提示；②安全类报警优先展示强制处置流程（如停机、通知班组长），不让模型自由发挥；③规则引擎结果与 AI 结果并行展示，若规则已明确判定，以规则为先；④提供“有用/无用/误判”反馈按钮，持续沉淀高质量案例；⑤上线初期由工艺/设备工程师共同审核 AI 建议，校准案例库和提示词。

### 8.8 需求范围持续膨胀影响 5 天 MVP 和一期交付

**风险描述**：项目覆盖采集、上传、大屏、分析、AI、配置、审计、运维多个方向，现场调研中容易不断追加新需求（如更多报表、更多设备型号、多端展示、外部告警接入），导致核心链路迟迟不稳定。  
**影响**：5 天 MVP 无法跑通，一期试点延期。  
**应对**：①严格以 5 天 MVP（海康采集→本地存储→MES 上传通道）作为第一验收关口；②建立“一期必须/二期补齐/三期以上规划”的分级机制，非核心需求不允许插队；③新增需求统一进入需求池，按对主链路价值和开发成本排序；④每周复盘范围偏差，避免大屏和分析功能提前抢占采集稳定性资源。

### 8.9 数据量增长对存储与查询性能的压力

**风险描述**：单车间 400~500 万条/天，青州 7 车间约 3000 万条/天，全集团 23 车间达 1 亿条/天规模。如果时序表建模、索引和聚合策略设计不当，会导致历史查询慢、磁盘快速占满、大屏加载超时。  
**影响**：历史分析体验差，平台在多车间推广时性能瓶颈暴露。  
**应对**：①时序数据统一采用 TDengine 超级表+标签建模，按设备和点位做子表，避免用 MySQL 存高频测点；②提前设计分钟、小时、班次、日聚合表，大屏优先查聚合；③定期执行数据归档和压缩策略，明确热数据/温数据/冷数据留存周期；④大范围历史查询和导出采用异步任务，避免拖垮实时接口；⑤在试点期持续压测，验证单车间、单基地、跨基地规模下的写入和查询表现。

### 8.10 多车间复制过程中配置不统一

**风险描述**：从青州试点复制到淮北、江西及其他车间时，如果设备命名、点位编码、班次口径、故障字典不统一，会导致模板无法复用、报表无法横向对比、复制部署效率低。  
**影响**：单车间部署时间无法压缩到 1 人日，平台化目标失败。  
**应对**：①从一期开始统一编码规范（工厂、车间、产线、设备、点位、故障码、缺陷码）；②点位配置支持“设备型号模板”，新车间先选模板再微调；③将配置项（点位、阈值、班次、字典、MES 参数）作为可导出/导入的资产管理，变更留版本和审计；④在青州试点阶段同步沉淀复制手册和标准验收清单；③每个新车间上线前执行标准化配置检查，避免现场临时随意命名。

### 8.11 现场组织协同与职责边界不清

**风险描述**：项目涉及设备商、电气、工艺、质量、MES 团队、IT 运维、车间管理层，各方提供点位、网络、账号、测试环境的节奏不一致，容易出现“等资料、等账号、等确认”的隐性阻塞。  
**影响**：开发完成后无法现场联调，试点时间被组织协同消耗。  
**应对**：①成立青州试点专项小组，明确业务负责人、IT 接口人、设备接口人、MES 接口人；②以清单方式提前列出依赖项（点位表、IP、账号、白名单、测试时间、验收人），每周例会同步进度；③对外部依赖设置明确截止时间，未按期提供的事项进入风险升级流程；④联调阶段固定现场窗口，减少零散沟通成本。

---

**风险控制总原则**：先跑通主链路，再扩展分析与 AI；先保证稳定采集和上传，再追求界面和高级功能；先形成可复制模板，再推动多车间推广。所有风险在试点阶段必须暴露并解决，不能把问题留到复制推广阶段。
