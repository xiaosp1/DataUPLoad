# 工业数据采集与智能分析平台 - 项目备忘录

> 创建时间：2026-07-06
> 状态：v0.2方案就绪，准备启动Day1 MVP开发（MES上传先行）

## 一、项目背景

为集团内部工厂开发工业数据采集与智能分析平台，核心三大块：
1. **数据抓取**：HTTP/OPC-UA/EIP 三种协议对接海康大屏、包装机PLC、手套点数机PLC
2. **数据上传**：HTTP 协议上传 MES 系统
3. **数据分析**：传统算法+图表 + AI 大模型分析

首站落地青州工厂，后续复制到淮北、江西等所有基地（共 23 个车间）。

## 二、已知范围

| 模块 | 数据源 | 协议 | 方向 |
|---|---|---|---|
| 采集-海康 | 海康视觉中控大屏 | HTTP | 拉取 |
| 采集-包装机 | 包装机 PLC | OPC-UA | 读取 |
| 采集-点数机 | 手套点数机 PLC | EIP（EtherNet/IP） | 读取 |
| 上传 | MES 系统 | HTTP | 推送 |
| 分析 | 采集到的全量数据 | 本地算法 + AI 大模型 | 分析+展示 |

## 三、第一轮需求澄清结论（2026-07-06）

### 产品定位
- 内部使用，多工厂部署（非 SaaS 产品，但要支持多基地复制）
- 使用角色覆盖全链路：一线操作工（大屏）、车间主任（报表）、工艺工程师（调参）、IT运维、管理层（BI）
- 端形态：先桌面端 → 后续扩展飞书/微信小程序 + Web 端

### 部署
- 现阶段：车间工控机（Windows）
- 后续：机房服务器集中部署
- 网络：同一局域网，可能有防火墙；需考虑断网/防火墙穿透/缓存续传
- 推广路径：青州试点 → 复制到淮北、江西、青州其他车间（共 23 个车间）

### 规模
- 包装机：每车间 8~16 台，OPC-UA 协议
- 点数机：包装机数量 × 2~4（即每车间 16~64 台），EIP 协议
- 采集频率：
  - PLC 定时轮询默认 **1 分钟一次**
  - 同时支持**数据变化主动上报**（OPC-UA Subscription / EIP 变化触发）
- 海康视觉：约 100 万条/天
- 数据留存：1 年
- 每台 PLC 采集点位：约 50 个（温度/压力/速度/计数/运行状态/故障代码/配方号/产量等）

### 规模精算（按 12 台包装机/车间，36 台点数机/车间，每台 50 点，1分钟轮询）
- 单车间：48 台 PLC × 50 点 = 2400 点位
- 每分钟采集：2400 条 → 单车间 ~345 万条/天（仅轮询）
- 加上变化上报 + 海康百万条/天，单车间约 **400~500 万条/天**
- 青州 7 车间：~3000 万条/天，全集团 23 车间：~1 亿条/天
- 一年留存：单基地 ~100 亿条，全集团 ~350 亿条（需时序数据库压缩）

## 三之六、第六轮需求澄清结论（2026-07-06 16:30）

### 海康数据获取方式重大调整
- **不是直接调海康设备HTTP API抓数据**，而是旁路抓取工控机上"海康采集软件"上传MES的HTTP流量
- 部署形态：我们的软件和海康采集软件**运行在同一台工控机上**
- 调试期MES可以停止（给我们切流/接管窗口）
- 含义变化：海康→MES的报文就是我们的"原始数据源"，我们需要做代理/旁路截获，再落地+转上传

### 范围裁剪
- 点数机：功能暂缓，但UI壳先做出来
- 包装机：功能等用户后续上传通讯文档，UI壳先做
- 首期核心链路 = 抓海康采集软件→MES的报文 → 本地落地 → （将来）转上传MES

### 工控机配置
- CPU：i7 12代，性能充足，边缘可承担更多计算（本地小模型、WebView大屏都无压力）

### 开发/调试分离
- 开发环境：用户本机（当前这台电脑）
- 调试/运行环境：运行海康采集软件的那台工控机
- 必须重点考虑：远程部署、环境差异、集中式日志、诊断包导出，否则现场问题难排查

### 待确认关键问题
- 海康采集软件里MES的目标地址是否可配置？（决定走"本地代理"还是"网卡抓包"方案）
- 上传是HTTP还是HTTPS？（HTTPS需要考虑证书问题）
- 海康采集软件上传MES的报文格式（之前整理过英科网关格式，是否就是那个？）
- 两台机器的网络互通性（本机→工控机文件拷贝/远程桌面是否可达）

## 三之三、第三轮需求澄清结论（2026-07-06）

### MES 上传方式
- 用户倾向**英科 dataportal/invoke 统一网关模式**（`/api/dataportal/invoke` + ApiType+Method 路由 + Ticket 认证），但尚未最终拍板，需评估
- 目前**没有 MES 接口文档**，第一步只做海康数据→MES，PLC 数据上传后续补
- 暂时无测试 IP

### 上传内容
- 产量/计数、故障/报警、质量缺陷、工艺参数、工单/配方结果、设备状态——**基本全传**
- 粒度：原始数据 + 聚合统计都要
- 触发：**定时批量 + 事件触发** 两种并存

### 可靠性
- 交付保证：**至少一次**
- 幂等：MES 侧暂无要求，先由**本地保证不重复发送**（本地生成唯一 ID + 已发送标记）
- MES 不可用：**本地缓存补传**；缓存满/离线太久（阈值可配）→ **人工导出 + 预警告警**

### 写 PLC（工单/配方下发）
- 来源：**两种都要**——MES 下发 + 软件本地界面手动录入下发
- 安全策略：
  - 软件端暂不做权限校验
  - 写入后由 PLC 端/HMI 人工确认点确定才生效
  - 写失败**报警但不重试**（避免误写）

## 三之四、待推荐方案

### MES 接口模式推荐
**推荐使用类似英科的统一网关模式，但建议做轻量化调整：**

| 方案 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|
| 英科式统一入口（/api/invoke + ApiType+Method + Ticket） | 协议统一、易扩展、后续加接口不用改路由 | 对小项目略重；MES 侧需要适配 | ⭐⭐⭐⭐ |
| 标准 RESTful（每个接口独立 URL + JWT 认证） | 最通用、好调试、生态成熟 | 接口多时需维护多个端点 | ⭐⭐⭐⭐⭐ **推荐** |
| MQ/Kafka 消息队列 | 高吞吐、解耦、天然支持补传 | MES 侧要部署 MQ，首期过重 | ⭐⭐（后期可加） |

**建议首期走标准 RESTful + JWT**：
- POST `/api/v1/messages/defects`（海康缺陷）
- POST `/api/v1/messages/alarms`（报警）
- POST `/api/v1/messages/production`（产量）
- POST `/api/v1/messages/parameters`（工艺参数）
- POST `/api/v1/messages/status`（设备状态）
- POST `/api/v1/messages/workorder-result`（工单执行结果）

优点：① MES 侧对接最省事，直接 JSON POST；② 方便用 Postman/curl 调试；③ 将来加 MQ 做异步解耦也不影响接口层。
如果 MES 侧已经有统一网关规范（比如英科那套），那就按 MES 的来，我们软件适配就行。

### 海康视觉采集
- 海康有官方 HTTP API，Windows 部署网页端，**直接 POST 调用接口抓数据**
- 第一期只抓文字/结构化数据：**缺陷记录 + 报警数据 + 其他文字字段**，图片暂不抓
- 采集方式：**定时轮询 + 事件触发（新报警）两种都需要**

### 包装机 PLC（OPC-UA）
- PLC 型号两款：**欧姆龙 NX102-9000、汇川 AC801**
- 采集点：温度/压力/速度/计数/运行状态/故障代码/配方号/产量，约 50 点/台
- 采集方式：**定时轮询（默认 1 分钟）+ 数据变化上报**（双模式）
- ⚠️ **需要写数据**：MES 下发工单、配方写入 PLC（双向通道）

### 点数机 PLC（EIP）
- PLC 品牌：**欧姆龙**（走 EtherNet/IP 协议）
- 必抓：设备状态、故障、节拍；其他点位后续扩展
- 与包装机关系：1 台包装机对应 **2~4 台** 点数机

### 采集共性
- **必须可视化配置点位**（地址、数据类型、采集频率、报警阈值等），不能写死
- 断网/离线：本地缓存补传 + 开关控制是否开启
- 时间同步：用户未考虑，由技术方案推荐（建议 NTP + 网关软时间戳兜底）
